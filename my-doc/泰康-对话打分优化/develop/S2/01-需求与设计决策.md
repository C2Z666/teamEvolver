# S2 需求与设计决策

日期：2026-11-12。本文描述待开发目标；配套入口见 [README](README.md)。

## 1. 业务问题

输入案例均已被选为整体优秀的对话。需要挖掘其中值得评价的表现，形成能用于后续评分的维度、行为指标和候选档位。

整体优秀不代表每句话或每个动作都优秀。提取应允许普通动作、局部反证、没有可复用亮点。客户表示认可不证明销售效果，客户拒绝也不自动否定 HWP 的全部表现。

S2 要解决的主要问题是：相同能力在不同案例组反复生成完整维度与评分口径，再进行昂贵归并；最终产物又把具体方法、业务任务和抽象能力混为平级评分项。

## 3. 已确定的产品边界

| 决策 | S2 规定 |
| --- | --- |
| 启动方式 | 原有创建任务入口，一个 job 自动完成整个流程 |
| 原始输入 | 直接原始对话或已有准备目录中的原始案例；旧分析产物不进入模型 |
| 结果共享范围 | 维度库属于本次 job，不自动读取其他任务或租户的维度 |
| 提取次数 | 每条成功案例一次，后续阶段引用 Evidence 或检查原文 |
| 归属顺序 | 先匹配已有维度，集中处理无法归属的材料 |
| 正式 ID | 宿主分配，模型只引用给定 ID 或生成任务内临时 proposal_ref |
| 全局性 | 全量 Evidence 有去向，全量案例完成候选维度适用性检查；不要求每个维度适用于所有案例 |
| 最终数量 | 核心维度 6—10 可作为展示目标，不是硬阈值，不据此删证据或强并概念 |
| 候选评分 | 维度稳定后逐维度生成一次；默认 0—3，允许 rubric_pending，保留 N/A、NE |
| 模型能力 | 使用配置中的 Seed，不引入更强模型作为必要前提 |
| 执行器 | 首版使用 OV Compile；业务阶段由 teamEvolver 编排 |
| 发布 | 不创建 Skill Candidate，不实际评分，不计算权重或正式总分 |

## 4. 三层资产必须分开

1. 评分维度：一个边界明确、可以独立判断的评价问题。
2. 行为指标：支持该评价问题的可观察表现。
3. 方法实例：实现某种表现的具体问法、顺序、业务对象和情境。

例如，“询问教育规划的原因”“探询退休后的生活目标”可以支持同一评价问题，但必须比较其目的和判定边界，不能仅凭“询问”二字归并。给两个备选约访时间、接受客户另提时间、等待客户核对日程，是可能互为替代的协商方法，不能成为全场景都要完成的三个计分项。

模型发现的关系允许为同维度、方法分支、不同评价目标、无法判断。向量相似度只生成比较候选，不直接创建这些业务关系。

## 6. 单任务与有限迭代

“一次运行结束”指一个用户任务自动完成多个内部阶段，不等于一次 LLM 请求或一个 Compile Task。

固定顺序为行为提取、初始建库、批量匹配、集中新增、全量检查、有限修订、评分口径、装配。检查不输出第二套行为库。发现遗漏时仅记录 issue 和原文定位，允许作为本轮修订依据，不再开放式重提取全部案例。

成功提取可以因进程恢复而从本 job 的持久化回执恢复；不得跨旧 S0 job 导入分析结果。网络结果未知时先对账，不能盲目重提取。

## 7. 提速目标与限制

主要减少重复的维度定义、评分口径和 Compile 固定开销，不省略案例覆盖与引用核对。匹配是短判断，统计和 ID 分配由程序完成。

全量原文检查会增加成本，不能预先承诺总耗时必然降低。验收需要分阶段记录模型调用量、Token、Compile 次数、等待与墙钟时间。模型任务数与 Compile 数量分别统计。

调整排序只能改善现有窗口利用率，不能作为 S2 的主实现。递归合并所有全文、将全量成员挂到维度正文、每个新案例都生成评分锚点，均不属于 S2 方案。

## 8. 候选标准的证据边界

从优秀案例可以归纳候选正向表现和局部反证，无法仅据此证明评分效度或成交预测能力。全量建库后再检查同一批数据属于内部验证；独立校准需要预留案例或未参与构建的新对话。

业务事实真值以正式材料为准。缺少合同、产品或公司规范时，记录 `reference_required`，保留可核对的沟通过程，不把口头承诺当作准确性示范。
