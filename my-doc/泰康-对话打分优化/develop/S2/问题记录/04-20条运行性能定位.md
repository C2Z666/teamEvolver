# 20 条运行性能定位

核验日期：2026-11-13。任务：`ovmine-692dbb9712a499ecb948df8a089eb523`。
统计使用本次只读快照中的 **120 个已结束 Compile**，不包含仍在运行的批次；完整数值、批次身份和分段见同目录 `04-20条运行性能统计.json`。未修改业务任务、配置或历史回执。

## 结论

主因是这条 S2 链路的执行方式：将大量内部判断拆成小任务，每批重复完整的知识 Compile，再将 JSON 回执作为知识资源写入，等待语义加工和向量化完成；当前宿主一次只推进一个 Compile，将这些开销串行累加。teamEvolver 普通数据库读写、轮询及本机 CPU 不是已测得的主要耗时来源。

前次把“平均每 Compile 6.4 分钟”称作模型耗时不够准确。Compile 包含业务模型流水线与产物写入后的维护，不能将整个时长归给模型提供商。

120 个已结束批次的累计宿主计时为 45,971.67 秒（12 小时 46 分钟），平均 383.10 秒。该口径不包含批次之间的阶段规划、受理间隔、退避，以及尚未结束的批次，不能当作完整任务总耗时。

| 分段 | 累计 | 占这些批次耗时 | 取证方式 |
| --- | --- | --- | --- |
| 业务 Compile 流水线 | 14,692.88 秒，约 4 小时 5 分 | 31.96% | 本机 bot task 的 created_at → updated_at；pipeline total_milliseconds 交叉核对为 14,677.41 秒 |
| 输出回执 content_batch_write 的后台处理 | 28,319.9 秒，约 7 小时 52 分 | 61.60% | 116 个成功批次按相同目标 URI 匹配内容写任务，时间范围与流水线结束时间匹配 |

| 宿主在远端受理之前及完成之后的批次内差额 | 154.57 秒，2 分 35 秒 | 0.34% | 宿主 compile_wall_seconds 减远端 tracker task 创建到 operation.finished_at |

## 根因一：内部回执走了知识加工通道

宿主 `v2/executor.py` 给每批创建独立资源目录，将阶段文件交给 OpenViking Compile。bot pipeline 在业务结果完成后调用 batch_write；内容写任务继续执行资源刷新，并等待所属 Semantic/Embedding Work 完成，随后外层 Compile 完成发布和版本记录。

源码链条：

1. `team_miner/skill_miner/dialogue_dimensions/v2/executor.py:73`：每批独立资源根目录与请求。
2. OpenViking `bot/vikingbot/compile/service.py:1187`：输出文件 batch_write。
3. OpenViking `openviking/storage/content_write.py:1297`：refresh_file_parents，触发内容语义维护。
4. OpenViking `openviking/storage/queuefs/content_write_processor.py:267`：等待该内容写任务的后续 Work 完成。
5. OpenViking `openviking/storage/queuefs/semantic_processor.py:1798`：目录 overview 生成还会调用 VLM。
6. OpenViking `openviking/service/compile_targets.py:1386` 起：输出目录索引、快照与版本发布；外部 Compile 本机后端状态查询周期为 30 秒。

例如 Compile `cmp_8d573bbfa522bd6cd75fed2d4fcc427ce572c91fd5ec880d9a6420d542bb06af`：

- 业务 pipeline 约 99.6 秒；bot task 从 10:55:07 到 10:56:46。
- 匹配内容写任务 `2db3c992-ddf6-45d6-8d4c-324545d738bc` 从 10:56:46 到 11:00:09，约 202.95 秒；结果明确记录 Semantic processed=1、Embedding processed=5，均无重试或错误。
- 远端 operation 到 11:00:39 才完成，宿主批次计时约 339.0 秒。

**这里的内容维护不是纯磁盘 I/O。** 它可能包括额外摘要模型调用、Embedding、索引更新和等待。现有持久记录能确认该层累计耗时，不能将其精确拆成摘要推理/Embedding/锁等待的各自占比。后台还实际观察到本任务旧批次的 parent_refresh 正在向父目录传播，进一步占用同一模型与维护资源；这些调用不包含在下面 1,091 次业务流水线调用统计中。

## 上下文、模型、重试分别承担什么

- **上下文超长不是已证实的首要原因。** 业务调用 Prompt token 均值约 11,302，中位数 9,738，最大 32,925；未见这轮因上下文超限停住。真实包最高字符数 11,965。重复模板、schema、维度卡和原文带来了 token 放大：业务流水线累计输入 12,330,606 prompt tokens；不能把这些累计 token 误认为某一次请求的上下文。
- **模型实际有成本，但单次业务调用不是数分钟。** Map 均值约 17 秒；业务流水线整体占已结束批次约 32%。规划/复核与摘要维护也会使用模型，所以“全是模型慢”与“完全无关模型”都不准确。
- **重试是额外损耗，不能解释大部分耗时。** 宿主语义重试 21 次，独立限流传输重试 4 次；内部 pipeline 另记录 validation_failures=126、repairs=126。这是两层口径，不能当成同一种重试直接合计。4 个终态 failed Compile 累计计时约 158.5 秒，另有退避间隔；大部分成功批次即使无错误，也仍花数分钟做内容维护。
- **teamEvolver 数据库/取回响应不是主瓶颈。** 对齐外层远端受理时间后，已测批次内宿主与远端差额平均 1.29 秒。初步用 bot task 创建时间计算的 5.89 秒，还包含约 4.60 秒远端启动过程；这部分不能全归给宿主。它的流程拆分、串行状态机、资源目录选择属于此次慢链路的设计责任，不能仅因为大段时间记在 OpenViking 就认为接入设计没有问题。
- **额外环境问题。** 队列观察到旧任务 `ovmine-7aa347dd0fe12d701fec7a7021acd4f8` 的一个 content_batch_write Work 在处理状态约 40 小时；本次观测普通队列 pending 基本为 0，无法据此认定它造成了本轮主要耗时。本轮主要内容维护等待已由对应任务记录直接量化。旧 Work 需要单独审计恢复，未擅自停止。

## 处理优先级

1. 给阶段输入/回执提供适合结构化制品的存取路径，避免每个临时回执都触发知识摘要、父目录维护和向量检索索引；最终需要检索的正式制品再统一加工。需保留不可变原文、版本、哈希、幂等和回执验收约束。
2. 对固定执行图复用确定性计划，减少每批入口、重新规划和通用复核；宿主已做的 schema/身份检查不应反复交给模型重做。
3. 将遗漏先做语义归并，批量比较并复用未变化的目录卡/比较结论，降低 845 次比较和重复登记开销；保留最终全目录覆盖的证据。
4. 在前述无效工作量下降后，改造为多个可持久化在途批次，按阶段冻结版本并做有界并发；结合账户 TPM 管理，不直接盲目增加并发。
5. 对摘要、Embedding、排队、锁、快照分别补齐 task 级 wall time 和 token 指标，展示中间结果。

这些是针对实测根因的修复方向，尚未作为性能补丁实施，也没有对当前正在运行的测试做中途改配置。不能宣称提速倍数。仅去掉已测输出维护部分，仍会留下约 4 小时的业务流水线累计耗时，因此只换模型或只调并发不足以解决整体设计问题。

## 补充核验：执行计划复用与额外 LLM 调用

用户追问后进一步逐批核对了已保存计划：116 个成功批次的 `plan.json` 中，program 只有 **1 个唯一值**，均为：

```python
files = p.map(sources, task=contract.extract)
p.finalize(files, into=target)
```

尽管图完全一致，仍记录 142 次 plan 模型请求（包括格式修复）。`pipeline.py:198` 在每个新 Compile 中直接 `model.ask("plan", ...)`，没有先查询可跨批次复用的计划模板。随后将计划写到当前 task 的 workspace；这份保存是任务产物，并不是新任务启动时的编译缓存。固定图应该按 Skill 版本、阶段和协议契约复用，业务数据的判断结果仍逐包生成。

Map 之后还执行 `review.py:257` 的模型复核。复核会调用 read_stage_output/read_evidence，再继续请求模型作出 continue/revise 决策；文件读取本身很快，工具返回后的再次推理才增加数秒到数十秒。412 次 review 指的是模型请求数，不是412次普通函数执行。

回执维护也明确会生成内容：

- 116 个成功输出批次合计创建 352 个结果文件，每批1—4个。
- SemanticTreeExecutor 对缺少可复用摘要的新文件调用 `_generate_single_file_summary`；JSON 属代码样式文本，AST无法提供可用结构时走摘要 LLM fallback（`semantic_processor.py:1401`）。
- 文件摘要完成后，目录概述调用 `_generate_overview` / `_single_generate_overview`，后者在 `semantic_processor.py:1799` 再请求 LLM；并据输出形成 abstract/overview，再做向量索引。
- 目录改变时可能继续 enqueue parent_refresh，父目录概述同样可能请求 LLM。是否向上刷新受 freshness 阈值控制，不能把每层目录都当成必然调用。
- 当前服务 PID 69912 实际加载 `.local-data/ov.conf`；其中 VLM thinking=true，且没有显式 max_tokens。摘要调用未按用途传 thinking=False/max_tokens；因此继承模型配置，普通回执摘要也可能启用推理。未更改该设置。

所以“输出内容维护用了203秒”不能解释为“向量数据库写入用了203秒”。已持久化记录将这个区间定位为包含 Semantic/Embedding 后续 Work 的内容写任务；其内部摘要模型、Embedding、等待各自的精确占比仍缺任务级调用计时。未将配置推断伪装为逐调用测量。

任务拆分程序本身不需要数分钟。它增加的是后续 LLM 工作：例如首轮20案例×13维度得到260个审计判断，分为80个模型任务包；登记与gap核对的845个关系比较分为184个模型任务包。每个模型包再进入上述完整 Compile，故几十毫秒的拆分动作可以导致数小时的下游推理和维护。应分别统计“必要业务推理”“重复规划/通用复核”“内部文件知识摘要”，不能把它们统一归为业务分析。

## 责任边界与只改 TE 的可行性

重复规划和输出语义维护的具体执行代码位于 OV；本轮 S2 按小包反复调用通用 Compile，则是 TE 的接入选择。应区分“修复 OV 通用能力”和“在 TE 为固定 S2 流程选择适合的执行路径”。

现有 TE `dialogue_dimensions/transport.py` 已在阶段输入和最终文件写入时传 `defer_processing=true`，并检查 semantic_status/vector_status=deferred，因此这些 TE 主动写入不会自动做知识加工。最慢的回执写入由 OV Compile 内部发起，其 batch_write 没有传 defer_processing；只修改 TE 这个 transport helper 不能改变 Compile 内部输出行为。

若保留每个阶段包都通过 OV Compile 执行的架构，需要 OV 提供并实际使用可复用计划执行，以及输出 defer_processing 的接口契约。TE 不能通过缓存请求结果或追加提示词，使当前无条件规划的代码自动变成计划缓存。

若限定只修改 TE，可以沿用已存在的 Worker、固定 S2 阶段、冻结 Skill、PG 回执日志、模型调用网关和严格校验，将阶段执行适配器改为直接发出所需模型判断；中间结果保存在 PG，需存 OV 的文件走已有 deferred 写入，最终需检索的制品再显式加工。这条路径可以避开上述两项成本，但属于替换 S2 的执行接入方式，需要新任务做业务质量、断点恢复和性能回归；不是现有任务的简单配置开关，也不消除必要的业务模型调用。

## Evidence 提取阶段专项核对与架构约束

用户明确希望数据处理继续由 OV 执行、TE 保持简单，因此不采用在 TE 新增直接模型执行器的绕行方案。性能优化优先补齐 OV 的计划复用和中间制品延迟加工，再由 TE 接入；本次核对未修改两边执行代码。

从上述 120 批快照按冻结任务包的 stage 和输入目录核对，Evidence 提取涉及 8 次 Compile（6 次 completed、2 次 failed，包含补跑）。首轮每批最多 4 案例，因此不是每案例单独规划，而是每个新批次重新规划。单案例的 Evidence 判断仍分别执行。

首批 4 案例的入口约 17.1 秒、规划约 50.9 秒，整个业务 pipeline 约 141.3 秒，输出内容写任务约 253.0 秒，宿主批次约 431.4 秒。这里只涉及 Evidence 提取，尚无维度修订，因此输出知识加工并不以“某个维度改了”为前提。

知识加工是在新建或修改回执文件后，为文件形成摘要、生成所在目录的概述、按 freshness 策略可能刷新父目录，再执行相关向量与索引维护；摘要和概述可能调用模型。普通改文件名、写描述字段、维护目录条目本身不解释这些分钟级时间。此处未获得内容写任务内部各步骤的独立 wall time，不能将全部 27 分 28 秒归给摘要或向量数据库。

OV 已有可复用实现基础：

- `pipeline.py` 保存结构化 contract、program 和 typed nodes；`plan.py:parse_plan` 提供受限执行图解析与校验，算子执行与计划生成已有分离。
- `pipeline_io.py:JsonModel._ask` 有经校验的模型响应缓存，但保存在当前 TaskFiles 工作区，键包含完整 data 等上下文；不是同一 Skill 换一批输入即可命中的共享计划缓存。review 明确跳过该缓存。
- `skill_resources.py` 记录附件内容哈希并可检查依赖变化，可作为计划版本失效判断的基础。
- 语义维护已有内容变更检测和旧摘要复用；新批次的目录及回执文件是新资源，无法自然命中同一文件的旧摘要。
- content batch-write 已支持 defer_processing；当前 Compile 内部输出未传入，也尚未证明外层发布流程允许不等待语义与向量加工就完成，需要端到端补齐契约。

因此“已有复用基础”成立，“已有跨 Compile 的计划模板复用能力”不成立。应在 OV 内按 Skill 内容版本、附件依赖、执行契约及影响计划的参数管理模板，运行时绑定新输入与目标；不能只复制 program 而遗漏 contract、依赖和失效校验，也不能直接复用旧案例的 Evidence 结果。

### register 的 80 批具体做了什么

进一步读取这 80 批冻结输入中的 proposal、gap_ref 与 revision 字段，分类无混合批次：

| 用途 | 已结束批次（含重试） | 累计宿主耗时 |
| --- | ---: | ---: |
| 初始或新增候选维度登记前的关系比较 | 17 | 1 小时 36 分 41 秒 |
| 审计疑似遗漏与全目录核对 | 30 | 2 小时 46 分 32 秒 |
| 修订后候选维度再次登记前的关系比较 | 33 | 3 小时 40 分 23 秒 |
| 合计 | 80 | 8 小时 3 分 36 秒 |

register 不是数据库写入计时，也不是 80 个新维度。模型比较候选与现有维度的评价问题、定义及边界，返回 same_dimension、method_of、different 或 uncertain；程序在目录覆盖、版本及结果完整性通过后决定复用、登记、更新或暂缓。

本快照共有 216 个不同 register 业务包，已验收回执包含 1,009 个维度关系判断：different 960、method_of 25、same_dimension 24。首轮疑似遗漏为 38 条，当时目录有 13 维度；每包最多 6 个维度，因此每条遗漏分为 6+6+1 三页，共 114 包、494 个关系判断。这解释了为什么仅“核对遗漏”就产生 30 次 Compile。当前去重以案例身份、原文引用、建议问题精确文本为键，并未将不同案例中语义相近的遗漏先聚为同一问题。

候选登记也是一次只处理一个 proposal：与当前完整目录分页比较，等待结果，决定是否变更目录，再处理下一个；修订后的候选会排除被替换源维度，但仍与其余全部有效维度核对，避免更新后撞入其他维度身份。

同一 register 范围内，输出内容加工约 5 小时 22 分 21 秒，业务 pipeline 约 2 小时 8 分 6 秒（其中 plan 约 57 分 17 秒），其余启动/收尾等约 33 分 9 秒。因此 8 小时不是都在做必要业务比较；相同完整 Compile 与输出加工成本被重复承担。可优化相近 gap 的语义归并、按未变版本复用比较结论、执行计划复用、批处理和中间回执加工策略，同时保留完整目录覆盖的验收约束。
