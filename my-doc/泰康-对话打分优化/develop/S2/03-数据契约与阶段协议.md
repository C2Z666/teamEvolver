# S2 数据契约与阶段协议

日期：2026-11-12。以下为待实现的协议，不表示当前 v1 校验器已支持。业务规则见 [Skill](skills/taikang-dialogue-dimensions-s2/SKILL.md)，执行顺序见 [流程架构](02-流程与执行架构.md)。

## 1. 协议与版本

- 执行协议：`te-dialogue-dimensions.v2`。
- 模型任务包：`taikang.dimension-task.v2`。
- 模型回执：`taikang.dimension-result.v2`。
- 案例存档：继续接受已验证的 `taikang.dialogue-case.v1`，保留其原文和 case_version。
- 模型案例渲染：新增 `taikang.dialogue-model.v2`，有独立 renderer_version 与内容摘要。
- 最终交付：`taikang.dimension-delivery.v2`。

原始案例版本、模型渲染版本、Skill 摘要、维度版本分别记录。改变包装不应伪装成原文变化；改变原文必须生成新 case_version。

实现中使用 Pydantic 或等效明确 Schema，并由同一结构生成阶段输出 schema 和宿主校验逻辑。不要通过解析自由文本 notes 判断维度身份、适用性或档位。

## 2. 输入与句级定位

业务白名单为 course、chapter、knowledge_point、scene、dialogue_text，加宿主 case_ref/case_version。历史总分、评分理由、综合评价、改进建议不进入模型输入。

原文与完整 sentence_index 保存在宿主。模型视图采用逐句标注，例如：

```text
[s000003][HWP] 要是俩娃一路读到大学，您估算大概得准备多少？
[s000004][HWP] 现在这块‘排队付账’的钱已经存了多少呢？
```

每段 text 从冻结原文按索引直接切取，不修正 ASR、不改数字或标点；说话人标签是元数据。未被句级跨度覆盖的空白、角色前缀和其他文本也按原顺序保留为视图片段，不能在模型视图中丢失有语义的原话。宿主保留 span→原文映射并检查全部对话字符的可恢复性。

模型只返回句子 ID，不计算 Unicode 坐标，不抄写长引文。宿主检查 ID 存在、归属案例、说话人和实际跨度。角色不确定保留 unknown；不得把客户句子当作 HWP 行为。

单案例任务中的 sentence refs 是该 case 内的句子 ID。多案例 propose/revise/rubric 包采用宿主分配的 `span_ref`，对应 `{span_ref, case_ref, case_version, sentence_ids, text}`；text 从原文恢复。`support_refs`、`source_refs` 在这些包中引用 span_ref，不能直接引用可能在多个案例重复的 s000001。member_ref/evidence_id 与 span_ref 分开校验。

## 3. 宿主持久化对象

下表是逻辑实体，实施时由 `dialogue_dimensions` 领域 Repository 管理；不要求每一行都独占一张表。

| 实体 | 必需字段及约束 |
| --- | --- |
| Run | tenant_id、job_id、execution_protocol、dataset_hash、skill_body_snapshot、skill_hash、config_revision、options、stage、delivery_status |
| Unit | unit_id、stage、input_hash、registry_revision、dimension_versions、attempt、status、request_key、remote_task_id、receipt_hash、parent_unit_id |
| Evidence | evidence_id、case_ref/version、local_ref、behavior、evaluation_question、trigger/action/response_refs、value_status、limits、business_fact_status |
| Proposal | proposal_id、unit_id/local_ref、card、evidence_ids、dispositions、register_status |
| DimensionVersion | dimension_id、version、registry_revision、card、previous_version、status、change_reason、support_links |
| Membership | evidence_id、dimension_id/version、relation、method_text、decision_ref、value_status |
| Audit | case_ref/version、dimension_id/version、applicable、sufficient、signal、support/counter_refs、reason、unit_id |
| Rubric | dimension_id/version、rubric_status、applicability、anchors、method_rules、calibration_notes、receipt_ref |
| Issue | issue_id、scope、reason、source_refs、status、blocking_scope、resolution_ref |

Evidence 唯一性由 `(tenant_id, job_id, case_ref, case_version, accepted_extract_unit, local_ref)` 保证；成功 extract 回执固定后，重复消费返回同一 evidence_id。不同 attempt 的回执不能被合成两套发现。

dimension_id 是宿主生成的不透明稳定 ID，不由标题、窗口或当前成员列表哈希生成。语义变更生成新 version；归并保留 source_id→canonical_id 的版本化别名，拆分保留父子关系。历史 Evidence、关联和 audit 不物理覆盖。

## 4. 定义卡 Card

所有 propose、register、match、audit 使用同一结构：

| 字段 | 类型 | 规则 |
| --- | --- | --- |
| name | string | 简短能力/表现名称，不是产品名或长动作串 |
| question | string | 一个可独立判断的评价问题 |
| definition | string | 评价对象及范围 |
| applicability | string | 有哪些情境和表现机会时适用 |
| boundaries | string[] | 不评价什么、与邻近维度怎样区分 |
| indicators | string[] | 可观察指标，允许方法互相替代 |
| scope | core / scene / undetermined | 暂定展示范围，不由知识点名称直接决定 |

召回短描述可以单独生成，但匹配和审计必须获得足够的 question、definition、applicability、boundaries。超预算应拆包，不能截断决定边界的字段。全量来源成员不附在每张卡后面。

## 5. 模型任务包与统一回执

任务包结构示意；其中示例 ID 仅说明字段，不属于实际 Evidence：

```json
{
  "schema_version": "taikang.dimension-task.v2",
  "execution_protocol": "te-dialogue-dimensions.v2",
  "unit_id": "unit-0042",
  "stage": "match",
  "input_hash": "host-computed-digest",
  "registry_revision": 3,
  "output_path": "analysis/dialogue_dimensions/receipts/unit-0042.json",
  "payload": {
    "evidence": [],
    "dimensions": [],
    "allowed_candidates": {}
  }
}
```

`input_hash` 对不含该字段的规范化任务包计算。宿主生成 packet，不由模型补 hash。真实任务中的 evidence/dimensions 等必须与分配内容一致，空数组示例不能照抄为分析结果。

所有模型回执统一为：

```json
{
  "schema_version": "taikang.dimension-result.v2",
  "unit_id": "unit-0042",
  "stage": "match",
  "input_hash": "host-computed-digest",
  "registry_revision": 3,
  "status": "analyzed",
  "result": {"decisions": []},
  "issues": []
}
```

status 为 analyzed 或 analyzed_with_issues；没有工作内容时仍需提供该阶段完整空结果及 reason。registry_revision 在 extract 可为 null，其余阶段取任务值。issues 使用 `{reason, refs, detail}`，refs 只能引用当前任务内已知业务 ID/句子 ID。

## 6. 各模型阶段契约

### 6.1 extract

payload：一个 case，含白名单元数据、带 ID 的完整对话和角色信息。

result：`observations[]`、`empty_reason`。每条 observation 必需：

```json
{
  "local_ref": "o1",
  "behavior": "询问目标费用及已经准备的金额",
  "evaluation_question": "是否将客户目标转成可讨论的资金需求",
  "trigger_refs": [],
  "action_refs": ["s000003", "s000004"],
  "response_refs": [],
  "value_status": "support_candidate",
  "limits": [],
  "business_fact_status": "not_involved"
}
```

value_status：support_candidate / mixed / routine / uncertain。business_fact_status：not_involved / reference_required / supported_by_supplied_reference。最后一项必须引用宿主实际提供的正式材料，否则降为 reference_required。

action_refs 至少一条可定位 HWP 句子，其他角色只能在 trigger/response。缺乏可用定位时隔离该 observation；其余发现保留。没有发现允许 observations=[]，填写 empty_reason。

### 6.2 propose

payload：`purpose=bootstrap|novelty|audit_gap`、evidence 或经过验证的 audit_gap 原文片段、少量相关定义卡。输入成员统一有宿主分配的 member_ref。

result：`proposals[]`、`dispositions[]`。proposal 为 `{proposal_ref, card, member_refs, rationale}`，proposal_ref 仅任务内唯一；disposition 为 `{member_ref, action, reason}`，action 为 routine / defer / existing_method，existing_method 还需 target_dimension_id 且该 ID 必须在输入中。

每个输入成员至少有一个去向，允许有解释的多重关联。最多 3 个 proposal，超出时剩余成员 defer，不丢弃。不输出评分档位，不分配全局 dimension_id。

audit_gap 引用直接定位原文，形成的是候选修订材料，不导入第二套 extract observations。

### 6.3 match

payload：`evidence[]`、`dimensions[]`、`allowed_candidates`。每条 Evidence 的候选集合由宿主明确提供。

result：`decisions[]`；每条输入 Evidence 恰好一项：

```json
{
  "evidence_id": "ev-001",
  "action": "attach",
  "targets": [{"dimension_id": "dim-001", "version": 1, "relation": "same_dimension"}],
  "method_text": "",
  "reason": "评价目标和判定边界一致"
}
```

action 为 attach / method_variant / unmatched / routine / uncertain；前两项必须有合法 targets，其余 targets=[]。relation 为 same_dimension 或 method_of。多目标仅用于不同评价目标，reason 必须说明边界，不复制同一能力形成重复计分。

模型不因不存在目标而创建定义，不因 mixed 而删除原有局部反证。宿主保留原 Evidence 的 value_status。

### 6.4 register

payload：单个 proposal、当前注册表的一个定义卡页面、page_id、registry_revision。没有任何已登记维度时由宿主完成空集登记，不必调用模型作空比较。

result：`comparisons[]`；对页面中每个 dimension 恰好一项 `{dimension_id, version, relation, reason}`。relation 为 same_dimension / method_of / different / uncertain。

不输出新维度 ID，不合并两个既有维度，不重写定义。宿主汇总全部必要页面后才决定创建或关联。对相同概念的多个已有目标不能随意选一个，进入边界修订。

### 6.5 audit

payload：单个完整原始 case、最多 4 个 definition cards，必要的已关联 Evidence 仅作辅助定位。

result：`assessments[]`、`uncovered[]`。每个给定维度恰好一条 assessment：

```json
{
  "dimension_id": "dim-001",
  "version": 1,
  "applicable": "yes",
  "sufficient": "yes",
  "signal": "mixed",
  "support_refs": ["s000003"],
  "counter_refs": ["s000011", "s000012"],
  "reason": "已有量化提问，但后续未处理客户提出的条件"
}
```

applicable 为 yes / no / unknown；sufficient 为 yes / no。signal 为 support / mixed / counter / not_demonstrated / na / ne。

- applicable=no → signal=na。
- applicable=unknown 或 sufficient=no → signal=ne。
- 其他情况从 support/mixed/counter/not_demonstrated 中选择；不能用片段缺失推断未完成。
- mixed 必须有支持与反证定位；support/counter 至少有对应定位。
- not_demonstrated 必须在 reason 解释明确表现机会，并用 counter_refs 定位触发与后续未处理的上下文；它不是单纯检索未命中。

uncovered 每项为 `{sentence_refs, issue, suggested_question}`，是有限审计问题，不是新行为库或新维度。不得据此为每句普通表达提出新评分项。

### 6.6 revise

payload：有限相关维度、程序计算的聚合指标、有限原文代表片段、可追溯 issues。

result：`changes[]`；每项含 `action, source_dimension_ids, reason, support_refs`，action 为 keep / update / merge / split / add / demote。

- update 给出 `replacement_cards`，只有一张；merge 给出一张，split 给出两张或以上；add 的 source_dimension_ids=[]。
- replacement_cards 每项为 `{proposal_ref, card, member_refs}`；member_refs 只能来自当前包已提供的 Evidence/audit gap。
- demote 给出 `target_status=evidence_only|needs_review`。
- keep 不改变版本；其他语义变化由宿主进入登记/版本更新并触发 recheck。

模型不能自行推断全部成员的迁移。宿主对旧成员补做相关 match，对所有案例补做变更维度 audit。

宿主应用 patch 时明确身份语义：update 保持源 dimension_id 并新增 version；merge 在来源中选择稳定 canonical_id，其他来源登记别名；split 为各子维度分配新 ID 并把父维度标为 superseded；add 分配新 ID。替换卡与其他现存维度的冲突检查排除其明确替换的 source_dimension_ids，不能因“与自己的旧定义相同”吞掉修订。新卡之间也要按登记顺序比较。demote 保留原定义及来源，不物理删除。

### 6.7 rubric

payload：一个最终维度及版本、适用条件、方法分支、有限支持/反证、scale=[0,1,2,3] 或明确给定量尺。

result：`dimension_id, version, rubric_status, applicability, anchors, method_rules, calibration_notes`。

- rubric_status 为 provisional 或 pending。
- applicability 为 `{when, na, ne}`。
- anchors 每项为 `{score, description, basis, source_refs}`；basis 为 observed / designed / mixed。
- provisional 必须覆盖宿主量尺中的每个 score；pending 可提供有把握的部分，并说明哪些档差尚不能建立。
- method_rules 说明替代关系、情境分支和重复计分边界。
- calibration_notes 说明未完成独立校准、哪些是设计推导及业务事实依赖。

不输出案例实际分数、权重、总分或成交概率。最高档不要求客户配合、成交或无必要的额外动作。

## 7. OV FileResponse 外壳

上面是业务 JSON，不是 OV emit 顶层。每个文件 Map 按实际 FileResponse 提交：

```json
{
  "files": [{
    "path": "analysis/dialogue_dimensions/receipts/unit-0042.json",
    "content": "完整的业务回执 JSON 字符串",
    "inputs": ["实际 assignment 顶层 inputs[].id"]
  }]
}
```

path 必须取 task.output_path；inputs 必须覆盖当前任务文件的真实 range IDs，不得使用 case_ref、evidence_id 或 unit_id 代替。较大输出可用当前 FileResponse 支持的 content_ref 替代 content，保留 path 与 inputs，不重复回传文件正文。

业务 schema 由宿主校验，OV 外壳按实际运行能力验证。对其他阶段或旧协议字段不做静默转换。

## 8. 宽松解析与严格来源

允许移除代码围栏、单对象转单元素数组、补入可由 task 唯一确定的 envelope 字段，记录 repair。可选说明缺失告警。重复关系去重由宿主完成。

不能自动补造语义结果、档位、证据或 missing dispositions。未知成员、外来维度、错误版本、篡改 input_hash、路径越界阻断当前单元。语义 uncertain 进入待核实，不反复重试直到模型强行肯定。

## 9. 聚合与评分目录

支持统计按唯一 case_ref/version 计算，不按 observation 数累加。audit 每个维度将案例互斥分为 support、mixed、counter、not_demonstrated、na、ne；另外显示存在支持的案例数 support+mixed，避免混淆两种计数。

分母为 applicable=yes 且 sufficient=yes 的案例，不以全部 171 条为每个场景维度的分母。模板家族分布与独立案例数分开报告，不声称统计独立性或评分效度。

## 10. 最终交付布局

```text
dialogue_dimensions_s2/
  index.md
  manifest.json
  validation.json
  run_metrics.json
  dimensions/part-*.json
  rubrics/part-*.json
  methods/part-*.jsonl
  findings/part-*.jsonl
  memberships/part-*.jsonl
  audit/part-*.jsonl
  coverage/part-*.jsonl
  issues/part-*.jsonl
  lineage/part-*.jsonl
```

只创建有内容或协议要求的实际文件，不生成空目录占位。manifest 保存输入/Skill/配置摘要、最终 registry revision、文件摘要、计数和状态，不嵌入所有正文。index 明确候选评分标准尚待校准。

coverage 分别记录案例提取、Evidence 去向、案例×维度 audit、最终 rubric 的覆盖。Evidence 可以有 routine/deferred 等合法去向，不强迫每条都进入评分维度。评分维度非空不代表全流程完成，零维度也不自动代表执行失败。
