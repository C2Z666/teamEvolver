# S3 需求与 Evidence 边界

## 1. 目标与范围

提取原文中可追溯、对后续归纳“什么情况下应如何处理”有价值的具体做法。这里的 Evidence 是实际行为及支持它的来源事实；方法描述是对行为的忠实概括，使用建议是单独标注的推断。

后续项目负责跨案例聚合、决定通用性和形成维度。S3 不为每条 Evidence 提前拟定评价问题、维度名称、评分档位、权重或价值分数，不维护共享维度注册表，不查询历史维度库。

全部对话已被选为整体优秀，不再给案例评优。但不将每个动作自动视为值得独立沉淀的方法；用户最后确认的“有价值的 Evidence”取代此前“所有动作都提取”的中间设想。

## 2. 三个提取判断

在同一次模型提取内依次判断，不保存第二套全量动作结果，不新增筛选 Compile。

1. **有实际行为**：销售 HWP 在当前原文中确实采取了该做法，有可定位的动作句。客户意向、分析者建议不能变成 HWP 已完成的行为。
2. **有具体方法**：能写出销售具体问了什么、怎样承接、如何组织解释、怎样安排步骤或说明前提；“建立信任”“体现专业”“挖掘需求”单独出现不够。
3. **有归纳信息**：行为至少包含具体的信息选择、表达方式、操作顺序、针对性调整、条件判断或边界处理之一。无需输出分类标签，亦不预设只能有这几类能力。

三个条件满足即可保留，不要求新颖、跨案例高频、客户正面回应或明显成交效果。条件没有在原文出现时允许为空，不能为凑全字段删除有价值行为或编造前提。

不设每案例配额，不设 Top K，不为了控制输出体积截掉后半段有价值行为；容量不足由宿主拆分任务解决。

## 3. 粒度

一条 Evidence 对应一个相对完整的沟通处理方法。紧密依赖、共同完成同一处理的动作放在一起；面对不同问题且可以独立说明的做法分开。

- 不是一句话一条，也不是一个动词一条。
- 不能把整场面谈压成“了解需求并介绍产品”。
- 同一案例内连续重复且没有新增信息，可以合为一条并保留全部必要动作引用。
- 同一案例中在不同触发情境再次使用相似做法，通常分别保留；不能因措辞一样丢掉不同情境。
- 不同案例中相似做法分别保留，以支持后续归纳的频率和情境分析。
- 姓名、数字、产品名替换本身不是方法差异；描述仍忠于本案例，不主动消除有意义的金额关系、顺序或业务对象。
- 长案例切分产生的机械重叠由宿主的责任范围和稳定身份消除，不进行新的语义归并。

## 4. 边界示例

下表除注明来源者外为说明规则的示例，不是本批对话的新增事实。

| 内容 | 处理 | 理由 |
| --- | --- | --- |
| 单独“你好、谢谢、嗯嗯、好的” | 不单独提取 | 通常没有独立方法信息，可留在上下文 |
| 原样重复客户一个词，未做进一步处理 | 通常不单独提取 | 不能仅因复述就推断已完成理解校准 |
| 概括客户顾虑并请客户确认理解是否准确 | 提取 | 展示了具体的理解校准做法 |
| 根据客户刚表达的担忧改变追问方向 | 提取 | 展示了有情境依据的调整 |
| 先确认客户方便程度，再约定交流时长 | 提取 | 常见但有可操作的安排方法 |
| 只罗列产品名或一组数字 | 通常不单独提取 | 未体现可归纳的处理方法；不因业务信息存在就制造行为证据 |
| 把产品信息对应到客户已经表达的需求解释 | 提取 | 展示了组织解释的具体依据 |
| 一句“客户很满意”或“客户同意了” | 不作为独立销售行为 | 可以作为实际客户回应引用，不能据此倒推销售做法 |
| 做法具体但权益口径无法确认 | 保留行为并标疑点 | 行为发生与产品承诺真实性是不同问题 |

离线展示中的真实例子：销售问候后说明共同介绍人，并转述介绍人对客户的评价。建议保留“说明共同介绍人的身份，并承接其具体评价开启交流”这一组合做法。不要独立产出“问候、介绍、赞美、信任”四条；也不能宣称已经使客户产生信任。

另一个真实例子是承接此前带娃交流，点明本次正式见面，再围绕客户对子女的关注开启话题。可保留其中具体的关系承接方法；不把“好妈妈”的判断升级为已证明的家庭规划能力。

## 5. 场景、触发与使用条件

| 内容 | 含义 | 事实要求 |
| --- | --- | --- |
| scenario | 当前关系背景、交流阶段及相关议题 | 来自当前原文或来源元数据，给出引用 |
| trigger | 直接触发做法的客户表达或对话状态 | 优先引用动作发生之前的内容；客户之后的回应不能倒作触发 |
| observed_conditions | 当前案例明确体现、与做法有关的条件 | 有原文/元数据支持；不混入应然建议 |
| suggested_applicability | 根据具体做法推导的适用条件 | 显式为推断，可为空；不能当来源事实参加后续频次统计 |
| response_refs | 原文实际出现的客户回应 | 不必积极；不因回应存在就推断因果效果 |
| uncertainties | 原文缺损、角色疑点、未核实口径等 | 局部描述，不扩展成独立合规审查或负向评价阶段 |

例如“场景三”只是来源标签，不能替代有内容的场景描述。销售自述由熟人介绍，可以记录为“销售说明由某熟人介绍”，不能据此声称介绍关系已经外部核实。

不要求编写每条行为的价值分析或通用风险清单。对“适用于首次交流”等建议，必须有当前做法作为推断依据；泛泛的“所有保险销售均适用”不输出。

## 6. 不确定与零结果

纯寒暄或只有客户表达的案例可以零 Evidence，但必须完整处理并给出简短 empty_reason。零结果不是失败，也不代表该案例不优秀。

具体做法有价值而某项条件不确定时，保留行为、条件留空或标疑点。不能以所有条件完整、所有角色无疑点作为全案例硬门槛。无法定位到任何确定 HWP 行为的条目不进入有效 Evidence；其问题单独保留，不连带删除其他有效条目。

不以“所有 HWP 句子都被引用”为验收条件。宿主的输入范围覆盖用于确认任务没有漏处理，与每句话是否形成 Evidence 是两种口径。
