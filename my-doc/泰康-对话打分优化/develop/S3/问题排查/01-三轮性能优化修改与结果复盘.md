# S3 三轮性能优化：修改、实测结果与后续思路

整理日期：2026-11-17（Asia/Shanghai）。本文汇总三轮性能优化的实现记录与终态核验，不修改历史任务或验收结果。

> 2026-11-17 回滚说明：用户明确禁止修改 OpenViking。本文第二轮的 OV 内部计时、第三轮的 OV 扩展参数及对应代码已撤回；当前项目改用未修改 OV 的标准 Compile 接口。以下保留历史实测，不代表当前能力或当前性能。详见 [回滚与兼容记录](02-撤回OV修改与标准接口兼容.md)。

## 结论

前两轮没有实现相对首测的提速：第一轮明显变慢；第二轮比第一轮回落，但仍慢于首测。第三轮定位并去除中间 JSON 的模型语义摘要开销后，最新 171 条全量耗时从此前的 29 小时 11 分 49 秒降至 7 小时 52 分 59 秒，累计减少约 73.0%，约为原速度的 3.70 倍。

这一全量对比反映三轮改动的累计效果，不能把全部收益归因于第三轮。20 条与 171 条的输入规模、长度分布不同，也不能直接用总耗时比较两者快慢。

## 第一轮：减少错误缩批和整条重提取，但真实运行反而变慢

### 实际修改

- 新任务冻结 `adaptive_policy_version=2`，2 单元起步、最多 4 单元，维持一个在途 Compile。
- 同一批量连续 3 批正常完成，实际 token 与耗时均留有至少 25% 软预算余量，才增加一个单元。避免用包含固定成本的单条耗时直接线性推算扩批成本。
- 字段隔离与普通回执错误不再触发全局缩批；限流、容量、超时或实际消耗超预算仍立即退避，缺少消耗观测不扩批。
- 正常提取优先；scenario、trigger、response_refs 等问题独立组批，只发送受影响 Evidence、原文与错误，返回受限字段补丁，减少为单字段错误重新提取整个案例。
- 补丁合并后重新完整校验；无效补丁保留原可用回执，修复次数有界，保存原回执、补丁、合并结果和修复 Skill 的血缘。
- 增加宿主阶段计时、扩批阻断原因和提取/修复类型展示，冻结历史任务策略。

### 预期与实际

预期是减少无效重提取与过度缩批。实际 20 条完整交付，但耗时 76 分 58 秒，慢于首测的 47 分 28 秒；正常提取从首测 5 批增加到 8 批，提交阶段观测累计约 37 分 46 秒。

原因是保守起步与扩批条件增加了小任务的 Compile 次数，每次仍承担规划、Review 和提交固定成本；本轮也尚未改变 OpenViking 提交路径。字段修复对存在坏字段的任务有价值，但不能据此认为这一轮 20 条测试已经加速。

## 第二轮：适度提高起始批量，补齐内部计时，仍未解决主要瓶颈

### 实际修改

- 每批从 2 单元调整为 3 单元，上限仍为 4，连续 3 批且有预算余量才增长，资源压力仍退避。
- 增加 `compile_input_soft_chars=9000`，按任务 JSON 总字符量组批，长输入减少同批数量；合法单单元可以独立超过软预算，避免截断原文或无法推进。
- 在 OpenViking 提交路径增加目录准备、目录索引队列/处理、标签可见性、输出锁、快照、差异计算、版本登记和冲突更新计时，透传至 PG、展示界面与导出。
- 未增加 Compile 并发，未修改提取/修复 Skill，未跳过索引或持久化检查。

### 预期与实际

预期是少跑小批次，并确定提交内部到底慢在哪里。实际 7 个 Compile 全部完成，20 条完整交付，产出 55 条 Evidence；耗时 59 分 32 秒，比第一轮改善，但仍慢于首测。

新增计时帮助定位了更具体的问题：

- committing 阶段观测约 30 分 41 秒。
- 7 个 `content_batch_write` 后台任务处理累计 **1799.71 秒，约 30 分钟**。
- 快照累计仅 **42.19 秒**。
- 输出文件锁需要等待语义摘要与向量索引处理结束才释放，中间 JSON 的语义处理占用了大量提交等待时间。

因此，这一轮的主要收获是缩小了排查范围。单纯调整批量并未去掉每批内部昂贵的提交处理；没有证据支持把主要瓶颈归因于快照或轮询频率。

## 第三轮：中间结果只建向量索引，去掉模型语义摘要

### 实际修改

- 新 S3 任务冻结 `output_vectors_only=1`，正常提取与字段修复均显式传入 `output_processing_mode=vectors_only`。
- OpenViking、Bot 和实际批量写入客户端完整透传、校验并持久化这一参数；仅允许 resource 目标。
- 对这些中间结果省去模型语义摘要，保留原文向量索引。输出锁仍等待处理完成，目录索引、标签可见性、快照、版本登记及业务引用校验继续执行。
- 策略进入幂等标识；模式变化不复用旧模式的增量进度；历史任务缺少参数时保持原行为，普通 Compile 默认路径不变。
- 每批 3 单元起步、最多 4、9000 字符软预算、一个在途 Compile，继续维持稳健调度。

### 全量实测结果

| 指标 | 优化前 171 条 | 第三轮后 171 条 |
| --- | ---: | ---: |
| 总耗时 | 29:11:49 | 07:52:59 |
| 已验收执行单元 | 173/173 | 173/173 |
| Compile 次数 | 221 | 104 |
| Compile 完成 / 失败 | 201 / 20 | 103 / 1 |
| 模型调用次数 | 1773 | 1064 |
| 输入 + 输出 token | 27,250,762 | 16,369,359 |
| 限流传输重试 | 18 | 2 |
| 完整 / 部分验收案例 | 158 / 13 | 163 / 8 |
| Evidence 数量 | 724 | 729 |
| 隔离 trigger 字段 | 16 | 15 |

token 合计不再重复加 cached token，它是输入中的缓存部分。Compile 失败次数、字段修复次数和单元重试次数属于不同口径，不应混用。

最新运行匹配到的 373 个后台批量写入任务（包含输入与合并回执的 deferred 写入）处理时间合计约 **108.23 秒**；输出任务没有执行语义摘要，向量处理没有错误或重排队。这与前一轮仅 20 条就消耗约 30 分钟的后台处理形成明显差别，支持“中间结果语义摘要是可消除的重要开销”的判断，但不是严格同规模的单变量耗时实验。

当前主要耗时已转向模型执行：模型调用区间合并后的墙钟覆盖约 **6 小时 40 分钟**；快照累计约 **8 分 46 秒**。不同模型阶段可能重叠，阶段时间不能直接相加为总耗时；轮询也可能遗漏快速阶段，不能把未观测到的提交时间当成零。

## 加速后的结果差异与验收边界

两次全量输入 171/171 逐案一致。主要提取规则保持一致，新增的是独立定点修复段；组批、修复策略和模型随机性仍会影响最终结果。

- 120 个案例 Evidence 数量相同，28 个增加、23 个减少，净增加 5 条。
- 以“案例 + 动作句子”去重，旧版 2724 个锚点、新版 2714 个、交集 2642 个；覆盖旧版约 97.0%、新版约 97.3%。这是动作引用重合度，不是全文或语义正确率。
- 旧版 12,077 次、新版 12,575 次引用检查均未发现案例归属或动作角色错误。
- 8 个旧 partial 案例变为 complete，但也有 3 个旧 complete 变为 partial；最新 15 个隔离字段均为 `trigger_after_action`。
- 局部行为粒度仍不稳定，例如 `case_6c4af35e7e80f6646239d192` 从 8 条合并为 4 条，`case_e5e7357655601fc793f127dc` 从 9 条拆为 13 条。这会影响下游独立复用，不能只看总条数。

总体没有看到明显的内容缩水，但没有对全部 Evidence 做人工语义标注，也没有多次重复实验，因此不能宣称质量完全等价或统计上显著提升。

最新任务已执行完全部 173 个单元，没有 failed/deferred 单元；因 8 个案例仍有隔离字段，以 `partial` 交付，界面映射为 `interrupted`，不是运行崩溃，也不是全部业务字段通过验收。

## 后续改进思路（尚未实施）

1. **先稳定行为粒度和 trigger 时序。** 开场动作与后续回答若由不同客户表达触发，应拆成独立行为；为每个行为明确起始动作和可用前置引用。没有可支持的前置触发时如实表达，不用后续客户发言补齐。继续保留时序门禁。
2. **减少修复往返，而不是增加无上限重试。** 最新 11 个字段补丁 Compile 累计约 40 分钟。向模型提供具体合法引用范围和错误位置，优先覆盖现有 8 个 partial 与 3 个回退案例；保留原回执和有界回退。需要拆行为的错误不能仅靠修改 trigger 字段解决，应先定义可审计的结构修复合同。
3. **围绕模型执行重新分解成本。** 分开统计规划、Review、提取和补丁的调用数量、耗时、输入输出与缓存命中，优先减少重复上下文和无效往返。保留必要审查，不能看到 Review 耗时就直接删除。
4. **保持保守批量，再做单变量验证。** 暂维持 3 起步、4 上限和单个在途 Compile。按短、中、长对话分别比较实际 token、长尾耗时、限流及质量；确认余量后再调整阈值，不直接扩大并发。
5. **把性能与质量一起验收。** 固定输入、Skill 和模型配置，对同一 20 条及长对话回归集重复运行；同时比较总耗时、调用数、限流、完整案例数、动作覆盖、行为粒度和 trigger。验证后再全量，避免把模型波动误认成优化收益。
