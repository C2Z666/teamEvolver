# S3 执行架构与运行优化

## 1. 固定执行路线

TE 负责确定性准备、预算、状态和校验；OV 依据冻结的编译 Skill 执行模型任务。PostgreSQL 是任务、回执消费和配置的唯一可变权威源，OV 保存 Compile 与知识制品。继续使用现有 Worker、平台 OV 客户端、admission 和租约，不新增 TE 直接模型执行器。

```text
prepare：校验来源、冻结原文/句子索引/Skill/参数
plan_units：每案例建立有界提取单元，超长案例分段
extract：循环提交有界 Compile、等待、校验并消费独立回执
assemble：从已验收结果确定性装配 Evidence 与完整性清单
delivery：生成跨项目包，结束为 complete / partial / failed / cancelled
```

每次 Compile：Entry 尽早 needs_pipeline=true → 一次文件 Map → OV 内部 Review → Finalize → 输出加工与发布。没有 Reduce、Shuffle、全库重读、共享维度或最终模型汇总。

新任务不得复用 S0/S2 的分析回执。任务重启或网络重试可以复用当前 job 已冻结且已验收的结果，这属于恢复，不属于重跑两套提取流程。

## 2. 单元、批次与并发

- Unit：一个完整案例，或该案例一个有界责任片段；一个 Map child 处理一个 Unit，输出一个回执文件。
- Batch：若干独立 Unit，共享一次 Compile 受理和发布，但不在业务上聚合。
- Job：包含全部来源案例、所有 Batch 和最终导出，用户只启动一次。

首版禁止多个案例拼成一个 Map child 来减少文件数。相同案例的完整输入不能因“批次更大”而进入其他 child。一次 Compile 的批次数量增加，不代表所有环节上下文都不会增长：Planner 的来源摘要、Entry、Review 的读取以及输出必须独立评估。

首版保留一个 active Compile。OV 内部 Map 并行度和模型账户 TPM 分别核对，不能认为 TE 单批就只有一个模型请求，也不能认为 TE 的 LLM 并发槽直接限制了 OV 服务端调用。增加多在途 Compile 不属于本阶段必做优化。

## 3. 批量和预算的初始值

以下是开发起点，不是经过 S3 实测的安全承诺。任务受理时冻结参数，运行中的安全降级另存有效参数和原因。

| 参数 | 首版起点 | 含义 |
| --- | --- | --- |
| cases_per_unit | 1，固定 | 不通过多案例共享上下文提速 |
| packets_per_compile | 4；验证后目标试验 8 | 数量上限，预算允许时才装满；16 仅在 8 已稳定后作为另一次试验 |
| packet_input_chars | 12000 | 紧凑业务包字符上限，沿用 S2 起点，不等于模型上下文 |
| packet_input_bytes | 48000 | UTF-8 序列化字节上限 |
| compile_input_chars | 32000 | 批次业务包累计上限；提高数量时不自动提高此值 |
| max_inflight_compiles | 1 | 明确保持串行批次 |
| semantic_repair_attempts | 1 | 每叶子单元初次调用之外最多一次语义/结构修复 |
| transport_retry_attempts | 5 | 网络/限流单独计数，结合已有 Retry-After 与退避 |
| capacity_split_depth | 3 | 初次确定性预切分之后，容量失败递归拆分深度上限 |

上限不足时提前发较小批，不能凑满数量而突破预算。不给 Evidence 设数量截断来“适配”输出上限。

实施时必须建立预算档案：模型标识、提供商上下文限制、实际 max_tokens、OV 有效输入预算、估算器版本、各环节历史峰值、修复/工具返回预留、账户 TPM 与来源。记录可用的实际值；未知项明确 unknown，不伪造上下文容量，也不读取或导出凭证明文。

预算同时检查：

1. child 完整输入：冻结 Skill、Transform 说明、实际工具 Schema、案例包、对话历史和后续读取/修复预留。
2. child 输出：依据代表案例实测估算完整 Evidence JSON、FileResponse 包装及推理输出占用；与实际单次输出限制一起判断。
3. 批次公共调用：Entry、Planner、Review 可能接触的完整上下文。通过调用日志或已验证的保守上界校准，不能只统计 task 文件。
4. TPM：一次批次可能并发的请求和维护调用也会占用配额。没有账户级精确数据时采取保守批次和退避，不承诺绝不限流。

字符数只是额外防线，不作为精确 token。只有实际上下文限制、输出限制与预算余量同时成立才扩批；资料不足时保持保守值，并在真实调用中记录峰值。OV fits() 是软字符预算，不能当本阶段安全证明。

## 4. 长案例与容量失败

先尝试一个完整案例。超出完整调用预算时，TE 按对话轮次确定性切分；单轮过长再按既有句子边界切分。不使用模型摘要替换原文。

每个片段包含 owned_sentence_ids（责任范围）和 context_sentence_ids（仅作上下文）。责任范围不重叠，叶子责任范围的并集覆盖该案例全部句子。优先带相邻完整轮次作为上下文；预算不允许时缩小责任范围，不截掉核心触发内容以便塞入。

模型只提交首个动作引用位于当前责任范围的行为；必要的其他动作、触发和回应可以引用当前可见上下文。宿主按原文顺序验证归属。跨界做法缺少完整后续内容时保留可确认部分并标 boundary_context_limited，不声称已完成看不到的步骤。该切分不能保证恢复无限长的完整语义链，验收必须单列边界损失。

容量降级规则：

- 公共阶段上下文失败：将失败 Batch 的未验收单元二分，已验收结果不重跑。
- 单个 child 输入/输出超限或返回 needs_split：拆分该 Unit 的责任范围，父 Unit 标 superseded，只消费叶子结果。
- 出现容量失败不原样重复同一超限请求；429 不能误判为输入过大而反复拆分。
- 单个不可再分句子超限、拆分深度耗尽、任务调用预算耗尽：终止该单元并记录 capacity_exceeded，交付 partial；其他单元继续。
- 每个 job 预先计算并冻结有限调用上限和总 deadline，覆盖初始叶子数量、有限拆分树及修复次数；超出即停止新提交并明确剩余项。具体时间值基于部署超时配置制定，不能无上限轮询。

“稳定执行完”表示没有无界循环、成功结果不丢失、失败有明确终态；不是以截断内容或伪造成功保证任意输入都能完整提取。

## 5. 可实施的性能优化

### 5.1 消除业务层多余阶段

S3 只保留 extract；删除新流程中的 propose/register/match/audit/revise/rubric 调度，不再生成评价问题、维度卡、覆盖矩阵和评分标准。完整性校验在 TE 中完成，不再新增一个“全量遗漏审计”模型阶段。

### 5.2 紧凑输入和有限扩批

单阶段 Skill 不携带 S2 的其他阶段。Schema 在 child 可见的执行契约中提供一次，不在每个 packet 同时重复 result_schema、receipt_schema，并在 instruction 再重复。原文只渲染一份，保留无损索引。

宿主 instruction 只保留固定传输约束和必要身份规则；Planner 的 Transform 必须完整保留提取规则与回执契约。不得为了缩短提示而让 child 无法获取必要 Schema。真实调用中验证重复量和完整性，不能靠字符串长度判断已优化成功。

一次 Compile 可以增加独立任务数量来摊薄规划和发布开销，但每个 child 的案例规模保持不变。批次由预算装箱决定，不按顺序遇到超长单元就把所有后续短单元永久阻塞。

### 5.3 减少重复写入和目录维护

- 冻结的编译 Skill 按内容 hash 命名；同一租户/账户/URI/hash 已验证存在时复用，远端缺失则重建。复用 Skill 资源不等于复用执行计划。
- 输入继续用现有 deferred 写入，校验真实返回状态，不对每个输入再主动触发语义刷新。
- 每批采用隔离、浅层目标目录，回执直接使用 `unit-xxxx.json`，不再追加 `analysis/dialogue_dimensions/receipts/` 多层子目录。保留账户和 job 隔离。
- 不将所有 Batch 写进不断增长的同一个可变结果目录，避免增量读取旧结果和重复刷新扩大。
- Compile 输出已在 OV 时，TE 只读回、校验、入 PG，不再逐个复制为另一套需立即索引的资源。最终按字节分片一次导出，走现有延迟加工能力或下载包，默认不额外触发检索索引。

浅目录能减少潜在目录维护层级，不能推导每层必然节省一次模型调用；每 Unit 一文件仍有加工成本。最终导出由 TE 确定性装配，不交给一个模型集中生成大文件。

### 5.4 不属于当前可用能力

不修改 OV 的约束下，不能用提示词保证跨 Compile 计划缓存、跳过内部 Review、令 Compile 内部 batch_write 延迟加工，或绕过发布等待。TE transport 的 defer_processing 不控制 OV 内部输出写入。Entry 直接完成虽在 OV 存在，但本方案明确禁用，不能作为失败回退或优化捷径。

## 6. 持久化、恢复和进度

提交前持久化 Batch 身份、请求幂等键、Unit 输入 hash、冻结 Skill hash。超时但受理状态未知时先查询同一幂等请求；不能立刻新建另一 Compile。

回执按 Unit 独立验收。严格绑定实际提交时的 input_hash、case_version、Skill hash 和 remote task；成功消费事务与 Unit 状态更新原子提交。旧 attempt 或已 superseded 父单元的迟到结果留作审计，不覆盖叶子结果。

OV task 失败但有可回读结果时，只有通过同等来源与完整回执验证的单元才可消费。只看到 scratch 文件或 running 状态不能算完成。

进度分别显示：来源案例数、完成案例数、完整零结果案例数、partial/failed 案例数、叶子单元数、有效 Evidence 数、隔离条目数、Compile 次数及耗时。分段完成一个 Unit 不等于完整案例完成。PG/OV 不可用时保留可恢复状态，不回退到本机权威存储。
