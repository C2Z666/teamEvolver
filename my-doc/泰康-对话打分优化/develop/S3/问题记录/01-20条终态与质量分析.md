## 3. 优先问题：trigger 与复合行为的时序契约不一致

7 次字段隔离经原始回执复核，全部满足同一条件：
trigger 引用位置晚于该 Evidence 的第一个 action_refs。

| 单元 / 条目 | 首动作 | 被判过晚的 trigger 引用 | 具体情况 |
| --- | --- | --- | --- |
| 003 / e1 | s000001 | s000003 | 用后续客户确认支持“此前带娃交流、今天正式认识”的开场背景 |
| 008 / e1 | s000001 | s000002 | 把问候与后续约访合为一条；客户“你好”位于两动作之间 |
| 009 / e1 | s000001 | s000003 | 先提出周二，客户冲突后改周三；中间回应确实触发后一步 |
| 014 / e1 | s000002 | s000003、s000004 | 把销售同一段开场说明的后续句作为整体行为背景 |
| 015 / e1 | s000001 | s000002、s000003 | 首次用途提问、客户未规划、继续引导合成一条 |
| 017 / e2 | s000007 | s000008 | 先问收入中断谁接棒、客户表达担忧、再提出补齐 |
| 020 / e9 | s000028 | s000029 | 先提议明天见面、客户询问时间、再提出下午两点 |

实现落点：

- [validation.py](../../../../../team_miner/skill_miner/dialogue_evidence/validation.py)：fact 的 trigger_before 检查，
  使用 `order[actions[0]]`；失败后清空整项 trigger。
- [delivery.py](../../../../../team_miner/skill_miner/dialogue_evidence/delivery.py)：任何 quarantined 项
  都让该案例变为 partial，当前同时统计字段与整条 Evidence 的隔离。

其中既有把后续确认当作前置触发的模型问题，也有真实连续交互被合为一条后无法表达中间触发的契约问题。
不能简单把阈值从第一个动作换成最后一个动作，否则真正的后果倒作前因也会被放行。

建议：

1. 明确 trigger 指“整条方法开始前的触发”，还是允许“方法内部后一步的触发”。
2. 维持前者时，将中间回应转为过程/条件依据；只对能独立处理不同问题的步骤拆条，
   不把每一句机械拆开。若确需表达多步触发，设计明确的动作—触发关联后再改 Schema。
3. 字段隔离保留具体错误码、原始引用、被清空字段摘要；
   当前 issues 只有 isolated_field + trigger，交付包自身无法直接还原根因。
4. 先修契约和确定性用例；是否需要模型补充依具体字段决定，不默认重跑全部 20 条。
5. partial 当前如实反映已隔离信息，不应直接修改历史状态或放松门禁使其变 complete。

## 5. 恢复问题与观测缺口

第 4 次 Compile 输入为 013—016，只输出 014—016 三份回执。
OV coverage 明确 1 failed、3 delivered；files-0 的错误为：

`Required agent transform ended without validated output:
Expecting property name enclosed in double quotes: line 1 column 587 (char 586)`

OV Review 明确保留这一失败后继续 Finalize，因此外层 completed 不等于全部 child 交付完整。
TE 逐份读回执发现 013 的文件缺失，将其 attempt 加为 1。
第 5 次 Compile 使用 013、017、018、019，最终 013 恢复成功；
第 6 次只处理 020。没有证据表明本次出现无限重试或必须人工补跑。

但有两个可观测问题：

- 页面/TE 的“语义修复 1”统计宿主重试，不包含 OV 的 19 次内部修复；
  内部修复还包含 Planner/Review 等阶段，不应全称为 Evidence 语义修复。
- 013 最终 accepted，但 unit.error 仍留着旧 404，coverage.units.reason 也会带入。
  建议区分 last_attempt_error 与终态错误，恢复成功后不要把历史错误显示为当前失败。
- per-case quarantined_count 计算所有隔离项，而 manifest.quarantined_evidence_count
  只计整条隔离。本批前者合计 7、后者 0；页面应标明“字段隔离 / 整条隔离”。

| 指标 | 实测 |

| OV pipeline total_milliseconds 累计 | 23 分 11 秒 |
| 两者差额 | 22 分 54 秒 |
| started_at 至 job 结束 | 47 分 28 秒 |
| pipeline 外的端到端差额 | 24 分 17 秒 |
| pipeline 已观测模型调用 | 86 次：Entry 6、Planner 8、Map Agent 48、Review 24 |

不保证包含 OV 目录加工等其他任务，也不换算为费用。

已排除“TE 只是隔几分钟才轮询一次”这一简单解释：
HTTP 日志中 TE 大约每 2.2 秒轮询，并在本地 pipeline 完成后约 0.6—1.4 秒就再次请求任务，
但数分钟后才开始验收回执。

OV 本地 compile_tasks 文件反映 pipeline 自身完成，服务任务终态还有其他流程。
当前 OV 代码的 CompileTargetLifecycle.on_finish 会等待目标目录索引/标签可见性及版本提交，
因此两个状态源不能当成同一终态使用。尚未用服务级分段时间完整分摊这 22 分 54 秒，
不能直接把全部差额归为某一种目录加工、锁等待或版本提交，也不能指称为 TE 空等。

建议先补齐“pipeline 完成 → 输出/目录加工 → 服务任务终态 → TE 消费”的分段指标，
再压缩不必要的格式修复、指令冗余和调度开销。现有约束不修改 OV 时，
不能承诺靠 Skill 关闭其内部 Review 或目录加工，也不应绕过正式任务终态消费未稳定产物。

S2 历史提取 Compile 累计约 47 分 41 秒，S3 本批约 46 分 05 秒。
两者提取目标、输出和并发条件不同，本次不能宣称显著提速，更不能据此决定 171 条的安全批量。
