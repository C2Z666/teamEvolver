# S3 数据契约与交付

本文定义待实现协议，不能直接由 S2 校验器消费。开发时用 Pydantic 或等效明确 Schema 实现，并由同一模型生成宿主校验与 OV 输出契约；示例中的 ID/hash 仅作说明。

## 1. 版本与输入

| 对象 | schema / protocol |
| --- | --- |
| 执行协议 | te-dialogue-evidence.v1 |
| 原始案例 | taikang.dialogue-case.v1，保留现有 case_version 语义 |
| 模型任务 | taikang.evidence-task.v1 |
| 模型回执 | taikang.evidence-result.v1 |
| 导出 Evidence | taikang.evidence.v1 |
| 导出清单 | taikang.evidence-delivery.v1 |

白名单为 course、chapter、knowledge_point、scene、dialogue_text 和宿主生成的 case_ref/case_version/sentence_index。历史评分、评语和改进建议不进入输入。不把业务元数据里的“场景三”当作具体适用条件。

原文和完整句子索引冻结在宿主；模型输入用保留原顺序的 fragments，每项含 text，以及存在时的 sentence_id、speaker。未落入句子范围的角色前缀、换行和其他文本也保留，完整案例视图拼接应能恢复原文。分段视图允许只包含分配范围，但必须明确列出范围，不能伪装为完整案例。

句子定位为 Unicode code points，零起点、左闭右开；不是 UTF-8 字节或前端 UTF-16 下标。原文不修正 ASR、标点、繁简或重复。角色为 HWP/C/unknown。模型不计算坐标、不抄长引文。

## 2. 模型任务 Task

必需字段如下；无 registry_revision、维度候选、历史 Evidence 或跨案例成员列表。

| 字段 | 类型与约束 |
| --- | --- |
| schema_version / execution_protocol | 固定为上述任务和执行版本 |
| unit_id | 宿主生成，不随同一次任务的普通重试改变 |
| stage | 固定 extract |
| input_hash | SHA-256；对排除 input_hash 的规范化 Task UTF-8 序列化计算 |
| output_path | 宿主指定 `unit-xxxx.json`，相对当前 Compile.to；child 不改路径 |
| case_ref / case_version | 对应当前唯一案例 |
| payload.metadata | 仅白名单元数据 |
| payload.fragments | 本单元实际可见的原文片段 |
| payload.scope | 下述范围对象 |

scope 为 `{kind, owned_sentence_ids, context_sentence_ids, segment_index, segment_count}`。kind=full_case 或 segment；完整案例 owned 包含全部句子、context=[]、index=1、count=1。分段编号从 1 开始；这是当前拆分计划的编号，重拆后生成新 Unit，不修改旧任务包。

scope 中 ID 必须存在于 fragments；owned/context 不相交，当前可见句子恰好属于两者之一。片段中的句子 ID 使用原始索引，不给同一句原话换一个新业务身份。

规范化使用 UTF-8、对象键排序、无多余空格、数组保留语义顺序、不做 Unicode 归一化。另记录 dataset_hash、renderer_version、Skill hash 和实际执行契约 hash；相同原文不同渲染不是同一个模型任务。请求幂等键至少绑定 tenant/account/job、执行契约 hash、Unit input_hash 和 attempt。传输重试先复用同一已提交请求身份，不产生并行重复提交。

正式 JSON Schema 由宿主集中编入 child 可见执行契约，不嵌入每个 Task 再复制一份。Skill 中的字段约定应与该 Schema 一致；生成器和样例验证用于防止两者漂移。

## 3. 模型回执

```json
{
  "schema_version": "taikang.evidence-result.v1",
  "unit_id": "unit-0001",
  "stage": "extract",
  "input_hash": "example-input-digest",
  "case_ref": "case-example",
  "case_version": "example-source-version",
  "status": "analyzed",
  "result": {
    "evidence": [
      {
        "local_ref": "e1",
        "behavior": "说明共同介绍人的身份，并承接介绍人对客户的具体评价开启交流。",
        "action_refs": ["s000001", "s000002"],
        "scenario": {
          "text": "销售以共同介绍人为线索开启本次交流。",
          "sentence_refs": ["s000001"],
          "metadata_refs": []
        },
        "trigger": {"text": "", "sentence_refs": [], "metadata_refs": []},
        "observed_conditions": [
          {
            "text": "销售在对话中说明自己由客户的朋友介绍。",
            "sentence_refs": ["s000001"],
            "metadata_refs": []
          }
        ],
        "suggested_applicability": [
          {"text": "存在可如实说明的共同介绍人时，可用于开启交流。", "basis_refs": ["s000001"]}
        ],
        "response_refs": ["s000003"],
        "uncertainties": []
      }
    ],
    "empty_reason": ""
  },
  "issues": []
}
```

### 3.1 字段约束

除 status/result/issues 外，身份字段逐字复制 Task，schema_version 使用回执固定值。所有数组必须为数组，缺省用 []，不得用字符串“无”。对象不允许未知字段，具体行为中可保留必要业务细节。

- status：analyzed / analyzed_with_issues / needs_split。
- result：仅 evidence 数组和 empty_reason 字符串。正常零 Evidence 必须说明 empty_reason；非空时 empty_reason 为空字符串。
- local_ref：当前 Unit 内唯一的 e1/e2 等，不是全局 Evidence ID。
- behavior：非空、具体、忠实于本案例；不使用维度标题或价值口号代替。
- action_refs：至少一个当前可见、确定为 HWP 的句子 ID；按原文顺序去重。首个动作引用必须属于 owned_sentence_ids。
- scenario、trigger、observed_conditions 元素采用 Fact：`{text, sentence_refs, metadata_refs}`。非空 text 必须至少有一项来源；空 Fact 的三项同时为空。conditions 中不放空 Fact。
- metadata_refs 只能是 task 已提供且非空的 course/chapter/knowledge_point/scene 字段名；引用不能自动证明描述的语义成立。
- suggested_applicability 为 Inference 数组：`{text, basis_refs}`，text 非空、basis_refs 非空且来自当前可见句子。该字段整体定义为推断，允许 []，不是事实条件。
- response_refs：当前可见、确定为 C 的句子 ID；只引用实际回应，通常位于相关行为之后。不得用客户回答反向证明行为有效。
- uncertainties：`{code, detail, sentence_refs}` 数组；code/detail 非空，refs 必须来自当前任务，可为空表示整体材料限制。不能只凭 detail 自由文本决定任务是否完成。
- issues：`{reason, refs, detail}` 数组；reason/detail 非空，refs 为当前案例可见 sentence IDs，可为空表示单元问题。与 action_refs 等同样依赖回执 case_ref/version 解歧。

trigger 允许引用 HWP 自述的当下状态，不限制只能 C；但引用发生在动作之后的客户回应不能解释为此前触发。未知角色保留上下文，不能自动当作 HWP/C。

needs_split 只用于无法在预算内完成：evidence=[]，empty_reason 说明容量原因，issues 至少一项 reason=input_capacity 或 output_capacity。它不是成功零结果，不进入有效 Evidence。不要以此代替正常的业务不确定。

## 4. 验收、隔离与幂等

| 检查 | 行为 |
| --- | --- |
| 非法 JSON、身份/hash 不匹配、路径越界、来源版本改变、缺完整回执 | 不消费该 Unit，按失败类型有限恢复 |
| needs_split / 上下文超限 / 输出截断 | 不消费半份结果，按架构文档拆分；不截掉尾部 Evidence |
| 单条 action_refs 越界、角色错误、空 behavior、owner 不符 | 隔离该 Evidence，其他有效条目可保留；案例标 partial |
| 仅缺少可选场景或推断条件 | 规范化为空并告警，不为补空字段重跑整个案例 |
| condition/inference 有坏引用 | 隔离该附属字段、保留可靠动作并记录降级；不能把坏引用静默改成无引用“事实” |
| 精确重复消费同一回执 | 返回既有结果，不新增 Evidence |
| 相同任务出现不同合法回执 | 首次已验收快照固定；后到版本记录冲突，不覆盖 |

宿主的可定位性检查不证明模型语义正确；是否“事实支持描述”“方法粒度恰当”由业务抽查验证，不再增加自动全量 LLM 复核阶段。

模型之外的错误分类由 TE 统一管理，例如 source_changed、invalid_receipt、missing_receipt、capacity_exceeded、transport_exhausted、deadline_exceeded。输入不完整等阻断问题即使模型返回 analyzed_with_issues，也不能作为完整案例成功。

Evidence ID 由宿主在接受事务内分配并持久化，唯一键至少为 `(tenant_id, job_id, unit_id, accepted_receipt_hash, local_ref)`；不能用标题作唯一键。重复消费固定回执复用同一 ID。一个 Unit 只允许一个已验收回执；替换父单元与激活子单元必须原子化，不能将两套结果同时加入交付。

不同 job 的重新提取允许获得不同 Evidence ID，导出另带 dataset_hash、case_ref/version、unit_id、Skill hash 等来源身份用于判断血缘；不声称语义相同会自动得到相同 ID。

## 5. 跨项目交付

最终包是 UTF-8 JSON/JSONL 和必要格式说明，无需依赖当前 PG 主键查询、临时目录、登录状态或活动 Compile。JSONL 每行一个完整对象；空文件也列入 manifest，分片规则按固定顺序及字节预算确定。

| 文件 | 内容 |
| --- | --- |
| manifest.json | 版本、dataset_hash、job 身份、Skill/配置/渲染摘要、完成状态、计数、文件相对路径/bytes/SHA-256 |
| evidence-0001.jsonl 等 | 每行一条 taikang.evidence.v1，保留完整模型行为字段，增加宿主身份与来源信息 |
| cases-0001.jsonl 等 | 所有输入案例的原文、完整句子索引、白名单元数据及 case_ref/version，包括零结果与失败案例 |
| coverage.jsonl | 每案例的 outcome、叶子责任范围、成功/失败单元、Evidence 数、隔离条目数及原因 |
| issues.jsonl | 未完成单元、隔离条目、降级字段与运行问题的结构化记录 |
| schemas/*.json | 实现中的正式输入/导出 Schema，供另一个项目校验 |
| README.md | 导入方式、事实/推断区别、partial 语义、定位坐标及无评分声明 |

导出 Evidence 至少增加 schema_version、evidence_id、case_ref、case_version、job_id、unit_id、receipt_hash、skill_hash、source_scope（来自 Task scope）。引用仍使用 sentence IDs，并由当前 Evidence 的 case_ref/version 消歧；这两个字段不能在展平记录时丢失。若未来改为跨案例引用，必须升级协议或显式使用带案例身份的引用对象。

模型不输出 quote。需要展示引用时，TE 根据原文和索引逐段截取，不拼接不连续片段为连续引文。导出包中的完整案例允许后续项目读取触发前后文，而非只拿一句压缩行为做聚合。

manifest 的 files 不包含 manifest 自身，避免自引用 hash；下载包整体校验值由 API 或旁置 checksum 提供。校验 JSONL 行数、外键、坐标和 hash 后才可声明导出成功。不得包含凭证、源系统鉴权 URL、运维日志或隐式依赖路径。

## 6. 完成状态

- coverage.outcome=complete：该案例所有叶子单元已处理，没有丢失有效条目；可有明确标注的业务疑点。
- zero_evidence：完整处理，合法零结果；不是 failed，也不是“未发现优秀案例”。
- partial：部分单元未完成或有 Evidence 被隔离，其他有效结果可消费。
- failed：该案例无法得到有效的完整处理结果；保留原文和原因。
- cancelled：任务取消导致尚未完成，已验收内容继续保留。

delivery_status=complete 要求全部案例 complete/zero_evidence，所有引用和文件校验通过；业务疑点不自动降为 partial，但字段隔离/来源缺失必须可见。部分案例失效则 partial；没有任何已完成单元且因执行错误停止则 failed。正常全批零 Evidence 可以 complete。取消任务为 cancelled，不伪装 complete。

后续项目默认只消费已验收 Evidence；遇到 partial 包必须显式知晓来源覆盖不完整，不能拿 Evidence 条数当全部案例分母。schema major 不兼容时明确拒绝，不通过猜字段静默导入。
