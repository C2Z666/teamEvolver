# S3 验证与验收

目标优先级：运行有界并正确结束 → 来源与行为可靠 → 下游可消费 → 在相同质量约束下提速。宽松业务验收不意味着允许身份错误、丢原文、伪造完成或无限重试。

## 1. 工程验证

长期用例放在 tests/miner/skill_miner/，按职责命名，例如 evidence_extraction_contract、evidence_budget_recovery、evidence_delivery。公共 fixture 放 tests/support；不从其他 test 文件导入，不依赖 my-doc 的真实历史输出。

必须覆盖：

- S0/S2/S3 协议分别路由；未知或结构错误协议拒绝，不能回退旧执行器。
- S3 只有 extract 业务阶段，Entry 被要求进入流水线，没有 Reduce、维度登记或评分调用。
- 默认资源打包存在，default/reset/effective/new job 快照一致；配置缺失、revision 冲突、一次性迁移和旧 job 冻结符合要求。
- 无损输入、繁简/ASR/换行/Unicode 坐标正确，客户句子不能成为动作，别的案例的同名句子不能混入。
- 合法零结果；局部条件缺失可以为空；坏动作引用隔离；坏附属条件不污染事实字段。
- 单元和批次分别计预算，超限拆分、不丢责任范围、不由扩大调度批次扩大 child 输入。
- 分段责任与上下文边界、同一句被多个片段看见只允许对应 owner 输出；跨界限制明确。
- 输出截断不消费半份 JSON，needs_split 不是零结果成功；最小不可分单元达到上限后 partial 结束。
- 未知受理状态用原幂等键查回；429 按限流退避，不误判容量错误；重试/拆分/deadline 有终点。
- 已验收单元不重跑；重复回执、迟到父结果、不同合法结果冲突、Worker 重启不重复产生 Evidence。
- 原始与导出计数守恒，完整零结果可以 complete，隔离/失败不能被完整成功掩盖。
- 导出不依赖当前系统，文件摘要、行数、句级引用和 schema 版本都能离线验证。

实施代码变更后按 AGENTS.md 执行 ruff、pytest；前端变更执行前端测试与构建；正式 docs/、路由、CLI 或环境变量有变化时执行文档引用检查及 docs 合约测试。测试规模按实际改动执行，不用文档校验代替运行验证。

## 2. 业务抽查

先使用现有 20 条原始案例，同时覆盖纯寒暄、具体破冰、客户顾虑、解释顺序、条件说明、无积极回应、单例方法、相似跨案例方法和长对话边界。人工补充的边界 fixture 要明确为构造用例，不冒充真实来源。

抽查问题：

1. 是否把纯问候、附和拆成独立 Evidence？
2. 是否漏掉有明确方法信息的行为，特别是低频场景？
3. 是否一条塞入多个独立处理，或把紧密组合拆得过碎？
4. 场景/触发是否有来源，是否把后续回应倒作前因？
5. 是否把推断使用条件写成事实，或者把销售口头说明写成已核实产品事实？
6. 是否有无引用的效果推断，例如“成功建立信任”？
7. 去掉系统其他信息后，下游是否仍能理解做法及原文上下文？

以人工标注的“值得保留做法”为参照记录召回、明显无方法信息条目比例、拆分/合并问题和事实/推断混淆，不以固定条数或字面一致作为通过条件。不需要提前抽出一套维度做金标准。

硬门槛：已验收 Evidence 的身份与定位全部有效；不能出现已确认的系统性漏尾、固定 Top K 截断或事实/推断字段颠倒。个别表达不佳允许记录问题，不能以此自动启动全量第二轮模型提取。业务是否可用由抽查结论说明，不虚构已经达到的准确率。

## 3. 性能实验

S2 历史提取基线：20 条原文合计 7077 字符，8 次 Compile（含补跑），批次累计约 47 分 41 秒，输出内容加工约 27 分 28 秒，规划请求累计约 7 分 50 秒。规划已包含在流水线内，不能与总耗时重复相加；这个数不是含批次间隔的完整 job wall time。

S3 与 S2 任务目标不同，不以 Evidence 数量机械对齐，不把去掉后续维度阶段带来的时间减少算成提取环节提速。

| 实验 | 条件 | 目的 |
| --- | --- | --- |
| A | S3 规则，1 案例/Unit，最多 4 Unit/Compile，保守预算 | 建立新目标的可完成基线 |
| B | 保持 A 的规则和预算，紧凑 Schema、浅目录、复用 Skill 资源 | 验证冗余压缩效果 |
| C | 保持 B，最多 8 Unit/Compile，总预算不自动提高 | 验证调度扩批是否减少 Compile 且保持完整性 |
| D（可选） | C 稳定后单独测试更大批次或经校准预算 | 不直接作为默认值，不并行提高多个参数 |

至少记录：端到端 wall time、批次 wall time、业务流水线、输出加工、批次间等待、Compile 数、重试/拆分数、单元/文件数、各模型阶段请求数、输入输出 token 峰值、截断/限流、有效与隔离 Evidence 数、业务抽查结论。可获得的实测值与估算值分列。

测量配置固定模型、Skill hash、原始案例版本和账户预算；记录其他任务负载。只在质量和完成性相当时比较速度，不宣称理论倍数。调度量增加后并行请求增多而变慢或限流，降回已验证档位。

小批通过后对完整 171 条做容量分布和一次全量验证，重点检查长案例、尾部任务、任务重启和整体完成状态；不能只凭 20 条短案例决定最大安全容量。为确认稳定性复跑时明确目的和样本，不把重复跑全量作为无条件例行步骤。

## 4. 跨项目导入验收

在不访问当前 PG、OV 临时目录和任务 API 的环境中，仅使用导出包完成：校验 manifest → 逐行读取 Evidence → 找到对应原始案例 → 还原全部引用 → 分离事实与推断 → 识别 partial 范围。这里仅验证导入，不开发下游维度聚合。

结果必须包含零 Evidence、partial 与失败案例的清单。下游不得把只含成功 Evidence 的子集误当全部输入，也不能把同一来源的重复导入算成新增证据。

## 5. 发布完成条件

- 新执行器、生产 Skill、协议校验、导出与前端共同可用，工程验证通过。
- 抽查没有系统性噪声提取、方法漏失或事实/推断混淆；已知局部问题可追踪。
- 目标案例范围有可解释终态；任何 partial 不得记录为“全量完整验收通过”。
- 默认编译 Skill 已在代码中切为 S3，安装产物包含资源；目标配置迁移完成，新 job 和 OV 使用正确 hash。
- 至少完成一次真实小批，并完成用于全量上线的长案例/全量验证；记录实际参数和性能，不以预计耗时代替结果。
- 最终交付包可离线导入，来源定位有效，用户不需要先运行 S0/S2 或再手动启动筛选阶段。

后续实施记录应写明代码版本、OV 版本、模型标识、配置/Skill hash、测试命令结果、任务 ID、输入范围、终态、分段耗时与剩余限制。未运行的检查写“未运行”，不得复制 S2 的通过结果作为 S3 证据。
